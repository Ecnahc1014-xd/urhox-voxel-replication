# 从占用数据出图纸（真投影 · 装配 · 可复现性）

本文件回答：**怎么把"体素/占用数据"变成一张可交付、可对账的图纸**，以及**开工前必须先做的三项体检**。
它不定义"像不像"（那是 `04`/`06`），也不定义注册链（那是 `02`）。

与其它文件的分工（不重复正文）：

- `02-drafting-and-registration.md`：图签容差、注册链与冻结流程（**输入侧**的制图）。
- `19-reference-image-intake-gate.md`：参考图能不能当输入（**入口闸**）。
- **本文件：从已有占用/体积数据反向出图（输出侧）**，以及它与渲染通道的对账关系。
- 外部绘制件（图幅/标题栏/导出）怎么采纳：`18`；跑它们要什么环境：`20`。

## 0 三条硬纪律

1. **出图三体检**（开工前逐项确认，任一未确认不得声明图可用）：
   （a）体素边长与其**反算来源**；（b）高度轴的**取值来源**；（c）**up 轴**。三项详解见 §1–§3。
2. **几何源与交付字节分开对待**：对账、回滚、跨轮比较一律认**几何源**（投影 JSON 一类）的哈希；
   **不得**拿 DXF/DWG 这类容器的 md5 当指纹。
3. **不得用出图替代渲染验收**：图纸是"占用关系"的证据，不是"画面正确"的证据（`12` 的通道分歧纪律照旧）。

## 1 体检一：体素边长不是全局常量

**现象**：同一个工作区里不同路线可能用不同体素边长。实测算例：

| 路线 | 反算边长 | 依据（两条独立体积） |
|---|---|---|
| A | 0.125 m | `origin_y 5.5 / minY 44`；`origin_y 4.0 / minY 32` |
| B | 0.25 m | `origin_y 6.0 / minY 24`；`origin_y 9.5 / minY 38` |

**后果**：用错**不报错**，只让整张图（以及所有从图导出的量测）**缩放错一倍**。图上完全看不出来。

**规范**：
- 边长必须由数据反算，不得由人凭印象填；反算方法取 `origin[up] / minUp` 的**中位数**（单样本易被离群体积带偏）。
- 必须用**另一独立字段**（如 `maxY`）交叉校验，不一致要在产物里留告警，不允许静默通过。
- 反算值、样本数、比值区间要写进几何源文件，便于下一个人复核。

## 2 体检二：节点盒高 ≠ 实心高度

**现象**：体积记录的 `size_<up>` 是**节点盒**尺寸，`minUp..maxUp` 才是**实心层范围**。两者常差很多。

**实测算例**：某体积节点盒 40 层 = 9.0 m，实心只占 12 层 = 1.5 m；直接引用会让该对象**虚高约 1.7 倍**。

**规范**：
- 高度轴一律取 **`minUp .. maxUp+1`**（注意上界是**闭区间 +1**），不得取节点盒高。
- 水平轴若数据未提供实心范围，只能用节点盒，**必须在几何源里标注该轴的取值来源**，并计入已知局限。
- 每个体积都要能回答"它的高度是从哪来的"；几何源里逐体积带 `ySource` 一类字段。

## 3 体检三：up 轴（最容易造成"看着像图其实不是"）

**现象**：数据是 **Y-up** 时（UrhoX 米制 Y-up 左手系即如此），`origin=[x,y,z]` 且 `minY/maxY` 就是竖向范围。
若按 Z-up 投影，`front`/`side` 会变成**"俯视样的立面"**——形状像图纸，实际完全不是立面，且**不报错**。

**规范**：
- 投影前先声明 up 轴，并按它定轴契约：

  | 视图 | 水平轴（Y-up） | **竖向轴（Y-up）** |
  |---|---|---|
  | front | X | **Y** |
  | side | Z | **Y** |
  | top | X | Z |

- up 轴的声明必须写进几何源文件（如 `upAxis` 字段），**不得只存在于命令行历史里**。
- 与 `19` §2 的轴契约对齐：`19` 表里的"Z 高度"是**通用写法**，落到具体引擎时"高度轴"以本节的 up 轴声明为准。

## 4 轮廓优先于矩形堆叠，且**优先用逐体素**

### 4.1 两种几何源，必须分清（这是最容易出错的地方）

| 几何源 | 怎么来 | 适合 | **不适合** |
|---|---|---|---|
| **体积盒**（node box） | 审计 `volumes[]` 的 `origin/size/minUp..maxUp` | 体量关系示意、缺逐体素数据时的傅底 | **当真三视图**。会把圆盘画成方块；实测体积比 **5.07×**（天守阁 24 盒） |
| **逐体素占用** | `voxcore.lua` 的 `kit.cells`（`Kit:Audit()` 直接数它计 `solid_cells`，是权威集） | **真三视图**（正交剪影 + 轮廓），体积精确可算 | 需要一次导出（见 §4.3） |

**判定口径**：只要产出物要当"工程三视图"用（对外交付、与渲染对账、作尺寸依据），**必须用逐体素**。
体积盒产物只能叫"体量关系图"，并必须随产物声明这一点。

### 4.2 为什么体积盒会差得很难看

盒的 X/Z 取的是**节点盒**（审计未提供 X/Z 的实心范围），而圆盘、环形、细长伸部这些形体
在节点盒里占据的体量远小于盒本身；多个盒还会重叠叠加。两个后果：
（a）**外形错**：圆盘→方块，分舰队分布/间距全部失真；
（b）**体积高估**：实测 5.07×（见 §6）。

### 4.3 逐体素导出与真三视图（工具）

| 步骤 | 工具 | 产物 |
|---|---|---|
| 1 导出逐体素 | `scripts/voxel_occupancy_dump.py --project <工程目录> --out <occ.json>` | `urhox-occupancy-masks/1`：三个视图位图 + 逐体积计数 + 真实体积 |
| 2 出真三视图 | `scripts/voxel_silhouette_drawing.py --occupancy <occ.json> --out <dir> --cadstack <cad_backend> [--compare-boxes <box_projection.json>]` | `projection.json`（voxel 级）+ `sheet.svg/dxf/pdf` |

导出**为什么走剪影位图而不是全格列表**：三视图只需要三个 2D 占用位图，
打包成 hex 只几 KB～20 KB；全格列表在日志通道上要几 MB～几十 MB。
同时逐体积计数一起给（真实体积 = `cells × voxelSize³`）。

**导出必须走日志通道**，因为离线 runtime 的 `File()` 写不了文件——详见 `20` §6.1（九条静默失败陷阱，含注入方式、Lua 作用域、稀疏表长度、并发串台）。

不传 --cadstack 时只产生 projection.json，退出码 0 只证明几何数据生成，不能据此说 DXF/PDF 已导出。逐体素投影保留占用行矩形，可直接接 projection_to_mask；三正交视图使用共同纸面比例。外部 CAD 的占位盒尺寸已清除，当前不提供尺寸标注；轴测是 top 剪影的示意投影，不是真三维轴测。

### 4.4 轮廓提取

1. 把几何投影到视图平面（逐体素时就是逐列占用）；
2. 按**体素步长**求并集；
3. 取"内→外"的边（四邻域判据），得到正交阶梯边；
4. 合并共线相邻段。

产物体量应同时保留**矩形/格子表**（可追溯：哪个体积/哪一格贡献了哪块）与**并集轮廓**（可交付）。
逐体素轮廓会很碎（实测某战舰 top 视图 12,764 段），所以图纸体积会比盒版大两个量级——
**这是正确的代价**，不要为了文件小回退到盒版。

## 5 与外部绘制件的分工（只借它擅长的）

现成的外部绘制件往往自带"从模型出图"，但其投影层常是**包围盒占位**（有的在注释里就写了
*"a full implementation would use the actual model geometry"*）。规范分工：

| 层 | 谁做 |
|---|---|
| 投影、轮廓、量测、几何源 | **本工程做**（本节 §1–§4） |
| 图幅、标题栏、视图布置、标注样式、DXF/SVG/PDF 导出 | 外部件（采纳等级与许可证见 `18`；运行环境见 `20`） |

接法：调外部件的 `add_view()` 后**覆盖其投影结果**（把本工程算出的线段写进它的视图对象），
再走它的导出。这样既不重写导出层，也不会把包围盒占位当成真投影。

## 6 可复现性

| 产物 | 可复现性 | 用途 |
|---|---|---|
| **几何源**（投影/轮廓 JSON） | **应当逐字节可复现**（同输入同输出，无时间戳、无随机序） | 对账、回滚、跨轮比较、写进证据包 |
| 图纸容器（DXF/DWG 等） | **通常不可**（库会写创建/更新时间与自增句柄） | 只作交付物，不作指纹 |
| 自绘 SVG | 取决于实现；若自绘则应与几何源同步可复现 | 交付与预览 |

**规范**：证据包里引用的是**几何源的哈希**；交付图纸另附文件名与字节数即可，不得用其哈希做判据。

## 7 出图与渲染通道的对账（怎么接）

出图本身**不构成**画面正确的证据。要把它接进验收，必须满足**同类比同类**（同 `04` 的模态规则）：

- **正交投影只能与正交渲染对账**；透视帧与正交投影求 IoU 是无效比较。
- 同一模型的投影与渲染对账只能证明两条产出通道一致，不能证明对原对象的忠实；保真结论必须另有独立参考。compare_masks 的 unaligned=null 表示配准未签核，不得读成 false。
- projection_to_mask 产出黑底白前景二值 PNG；与确定来源的渲染掩膜比较时须显式指定 --mode luma-fixed。全不透明图的 alpha、空前景与满幅前景均不能提供有效几何 IoU。
- **两侧掩膜都要有确定来源，不得靠亮度阈值猜前景**：
  - 投影侧：由几何源自算（按正交相机的 `orthoSize` / `res` / `center` 映射，注意**水平手性**可能需翻转且未必能由对称对象判别）。
  - 渲染侧：**必须用控制组**（同机位、同灯光、同时间，仅隐藏对象再渲一帧，两帧相减）。
    原因：正交渲染帧的 alpha 常是全 255；亮度 Otsu 取到的往往是“整幅暗部”（含地面、触满四边），
    据此算出的 IoU 与 size_drift 是**假失败**，看着像几何对不上，实则掩膜失效。
  - 差分掩膜必须自带**退化判据**（前景占比过高=对象未隐藏；过低=没差出对象），否则拿错帧也能算出数。
- **但“隐藏对象”的控制帧本身可能被证伪**（2026-09-23 实测）：
  把主体从场景里拿掉之后，**全局光照也变了**——控制帧退化为纯天空，连四角差异都 >60，
  差分掩膜被气氛变化污染（前景占比直接 = 1.0）。
  要让控制组成立，需要“**主体仍参与光照、只对相机不可见**”的能力（材质透明化、相机裁剪面一类）；
  当前引擎 API 不提供。建立控制组之前，先用**边缘一致度**（下条）作低成本替代。
- **边缘一致度作为低成本替代**（`scripts/outline_vs_render.py`）：把投影轮廓叠到渲染帧上，
  量“轮廓像素→最近渲染边”的距离分布（`refToRender`），并用 `bestPixelShift` 区分整体偏移与形状不对。
  它不是面积比，因此**不得冒充 IoU**；`renderToRef` 必然很大（渲染细节远超体积盒模型），**不得当缺陷指标**。
  首次实测值与读数见 `19` §3.1。
- 对账的指标定义、阈值与有效性域见 `14` §4；**在未取得本工程实测负样本前，外部惯例阈值不得进门禁**。
- 对账产物同样写进证据包，并注明"投影源版本 + 渲染版本 + 注册变换"三者的对应关系。

## 8 已知局限（照抄进每一份出图产物）

1. 按 sourceKind 标明粒度：盒版是体积盒并集；逐体素版是占用剪影，不得混称。
2. 水平轴可能取节点盒（数据未给实心范围时）。
3. 视图之间不做遮挡消隐（no hidden-line removal）。
4. 未与渲染帧对账前，不得声称"画面正确"。

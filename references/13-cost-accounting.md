# 成本核算（多线长期任务的可运营性）

本文件解决"**这条线到底烧了多少钱、比上次多烧多少**"。它与复刻质量无关，但与"能不能长期跑下去"直接相关；凡是并行多线、按轮迭代的任务都该有这一层。

## 1 数据源（不要估算，不要编单价表）

宿主/平台若在本地保存了真实用量，就用真实值。本工程实测可用的三类：

| 粒度 | 字段 | 说明 |
|---|---|---|
| 会话累计 | `sessions.total_cost_amount`（USD）、`total_token_usage`、消息数 | 每会话累计；**这是 per-scene 的主口径** |
| 按天汇总 | `daily_spend` 表 | 全应用口径的日花费，用于看总体节奏 |
| 每轮明细 | 助手消息的 `agentMeta`：`turnCostUsd` / `currency` / `approximate` / `kind=actual-cost`、`turnUsageDetails{inputTokens, outputTokens, cacheReadTokens, cacheHitRate, durationMs, perModelCost}` | 定位"哪一轮突然变贵" |

取数纪律：

- 先确认字段是**实际值**还是估算（看 `approximate` / `kind` 字段），估算值必须在报告里标明。
- **缓存读取占绝大多数 token 是正常的**：绝对 token 数大不等于贵，单价与缓存命中率才是解释项。
- 读不到就写 `UNVERIFIED`，不要用"单价 × token 数"自己算一个数出来。

## 2 口径定义（必须写进报告，否则数字会打架）

```text
per-scene 成本 = 该场景自己会话的累计 total_cost_amount
                （含该路线的所有世代会话：重开的、归档的、换模型前的 worker）
跨场景不重复计（Lead/主控会话单列）
按天成本 = 全应用口径，与 per-scene 不可直接相加比较
```

三条容易出错的规矩：

1. **按线归并要靠稳定的命名/标签**（会话标题关键词、worker label），而不是"当前活跃的那几个会话"——否则重开后成本会漏计。
2. **换模型/换 agent 不切基线**：同一路线换模型仍是同一条线，累计值应继续累加。
3. **增量必须有基线**：报告要给"较上次 +$X"，为此要维护一份基线文件（上次取数的时间与各线数值）。

## 3 一键脚本的行为约定

```bash
python -X utf8 <tools>/cost_report.py            # 出报告 + 更新基线
python -X utf8 <tools>/cost_report.py --peek     # 出报告，只读、不动基线
python -X utf8 <tools>/cost_report.py --json     # 机器可读，不更新基线
```

- 默认行为（更新基线）与只读行为（`--peek`）必须分开：**在自动化/定时任务里一律用只读档**，避免一次误跑把增量算成 0。
- 产物落盘（Markdown + JSON），不要只在终端打印。
- 报告里同时给：per-scene 表（累计 / 较上次 / tokens / 消息数）、按天表、口径声明、取数时间戳。

## 4 与交付、证据的关系

- 成本报告属**管理层一页纸**的支撑材料（见 `07-delivery-and-reporting.md`），不进验收证据包，不参与门禁。
- 定时播报（如"每 N 小时发一次"）要遵守两条：① 用只读档取数；② **本地落盘一份**，投递渠道（IM/邮件）只是渠道，不能成为唯一副本。
- 报告里禁止把成本当作质量或进度指标（"贵 = 做得好"是错的）；它只回答"花了多少、涨了多少"。

## 5 通用性边界

- 字段名与存储位置**随宿主产品版本变化**；换版本前先跑一次只读档确认字段仍存在，不存在就标 `UNVERIFIED` 而不是回退到估算。
- 若宿主不提供真实花费，本层降级为"可测量的消耗代理"（如轮数、token 数、时长），但**必须在报告标题里写明是代理指标**，不能与美元混排。
- 本文件不涉及预算分配与商业定价。

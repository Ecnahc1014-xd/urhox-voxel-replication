# 通道差异：离线渲染 vs 引擎内运行

本文件回答一个问题：**为什么"离线全绿"不能推出"运行起来能看"**，以及哪些缺陷只会在通道切换时暴露。

## 0 根因：两个通道不是同一套场景装配

| | 离线截图通道 | 引擎内运行通道（PIE / 编辑器） |
|---|---|---|
| 场景来源 | 脚本**自建场景** | 加载项目自己的 `assets/Scenes/*.xml` |
| 是否知道 baker / 烘焙节点 | **不知道**——这个通道里根本没有"baker 节点"这个概念 | 知道，且依赖它 |
| 是否加载项目配置（`project_info.json` / 编辑器配置） | 不加载 | 加载 |
| 是否建档可视化相机、角色 | 自带固定相机 | 由玩法/角色配置决定 |
| 能验什么 | 几何、材质、帧内容（逐像素） | 上述全部 + **接线、命名、取景、角色、烘焙链路** |

**结论**：下列几类缺陷**原理上不可能被离线通道发现**，因此任何交付前必须**至少跑一次运行通道**。

## 1 只在运行通道暴露的缺陷（实测清单）

### 1.1 烘焙节点与被摄体积根**同名** → 节点把自己删掉

> 同源命名陷阱在验收侧的后果（审计行/日志标签归属失配）见 `10` I-05。

- 现象：烘焙链路在初始化时"先删同名节点"，若 baker 节点名与体积根名相同，**删掉的正是 baker 自己**；命令返回成功、日志无红字，但烘焙不生效。
- 修法：场景 xml 里把 baker 节点改名（如 `<Name>Baker`），并**同步四处载体**：

```text
① 场景 xml 的节点名 + 其 LuaScriptInstance 绑定的脚本
② project_info.json 的 node 字段
③ bake_editor.py 里的 BAKER_NODE = INFO["node"]
④ subject.NAME（体积根名）
```

四者一致才算封死；只改一两处会留下"名字对不上"的新静默失败。

- **连带陷阱**：审计归属用的是**体积根名**（`subject.NAME`），不是 baker 节点名。所以改名后必须确认：① xml 节点名 ≠ 体积根名；② `BuildSubject` 不传 `rootName`（或传的值仍等于 `subject.NAME`）。否则审计标签会与归属失配。

### 1.2 出生点落在对象外 + 对象悬空 + 不建地面 → 角色无限下落

- 现象：运行起来角色一直往下掉、第三人称相机跟着飞走，画面里只剩天空；而离线帧完全正常。
- 修法：把出生点放到**可站立的实体面**上（如甲板/地坪），并确认对象有接地或平台支撑。

### 1.3 角色控制器**接管相机** → 悬空对象无法观察

- 现象：需要"静止整机镜头"来审视的悬空对象（飞船、空中基地），被角色控制器接管后镜头跟着角色跑。
- 修法：在共享角色脚本里给一个**可选开关**（如 `PLAYER.camera = false`），角色照常生成但不接管相机。该开关只影响取景、**不动几何**（改后重跑审计，指纹与体积数应完全一致）。

### 1.4 编辑器资源导入器把**证据图**注册成资源 → 重编码破坏字节级仲裁

- 现象：烘焙/打开编辑器后，证据目录里凭空多出成批 `.meta` + 贴图导入配置 `*.xml`（BC7 / ASTC 等）。实测一次烘焙产生 **22 个 `.meta` + 8 个导入配置**。
- 为什么致命：这些边车是**导入/转码的前置状态**——一旦导入真的执行，证据 PNG 会被重新编码；而"逐像素仲裁 + 逐轮逐字节相等链"整套体系**建在原始字节上**，链一断就全废。
- 机制：编辑器只对**新出现的**文件做导入。证据通常是"先写、后烘焙"，于是被当成新资源注册。
- 两层修法（**都要做**）：
  1. **根治**：项目编辑器配置（`.project/editor_config.json`）的 `resourceBrowserIgnoredDirs` / `fileWatcherIgnoredDirs` 把证据目录（`shots`、`docs`）加进去；
  2. **兜底**：烘焙脚本每次烘焙后自动清理边车并**打印清理条数**（只删"同名原始图仍存在"的 `.meta`/导入 `.xml`）。
- **怎么确认是根治层在起作用**：改配置后**重启编辑器**，扫描证据目录边车 = 0；再真实烘焙一次仍 = 0，且**兜底层打印清理 0 个** ⇒ 不是靠兜底删除兜住的。对照修复前：同一批已存在文件、同一操作，当时产生 22 + 8 个。
- 完整性复核：修复后应对证据做不变式检查（尺寸 / 字节数恒定、关键帧 md5 与冻结值一致、清单逐条匹配）。

## 2 怎么证明两个通道给的是同一代几何

不要用"看起来一样"，用**逐项相等 + 字节层差异**两条一起证：

1. **逐项相等**：运行通道日志里的 `build ok fingerprint=… / volumes=… / solid=… / overlap=0`，与离线终轮审计的对应字段逐项相等；有条件时做**全字段对比**（三指纹 / 逐体积 solid / stats / 接地率）。
2. **字节层必须不同**（更强的佐证）：两份审计若行尾不同（例如 CRLF vs LF，差≈每行 1 字节），**恰好反证它们是两个独立进程的产物**——同一份数据被两次归档不会在行尾分叉。

> 所以正确结论是"**两套独立实现对同一代几何给出同一结果**"，而不是"引用了同一个数字"。前者是证据，后者是环路。

## 3 通道检查清单（交付前逐条打勾）

```text
[ ] 至少跑过一次运行通道（PIE / 编辑器），且截图与日志已归档
[ ] 烘焙节点名 ≠ 体积根名；四处载体（xml / project_info / BAKER_NODE / subject.NAME）一致
[ ] 出生点落在实体面上；对象不自悬空
[ ] 悬空对象场景已确认相机是否被角色接管（必要时关掉）
[ ] 证据目录已进 ignoredDirs；烘焙后边车数 = 0（且兜底层清理数为 0）
[ ] 运行通道日志字段与离线审计逐项相等；有条件则全字段对比
[ ] 两份审计的字节层差异已记录（用于说明"两套独立实现"）
```

## 4 通用性边界

- 具体字段名、配置键名与"编辑器只导入新文件"这一行为，均以本工程实测为准；**换引擎或换大版本后必须重新确认**：是否仍有 baker/烘焙节点概念、证据目录是否会被资源扫描、忽略目录配置的键名是否一致。
- 本文件只覆盖"两个通道是否会给出不同结论"，不覆盖"结论本身对不对"（那是 `04` 验收与 `10` 仪器册的事）。
- 若项目只有一个通道（没有离线渲染能力），第 2 节的"双通道互证"改为"同通道两套独立抽取路径互证"（见 `10` 的 I-06）。
